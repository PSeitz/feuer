Lookup API

get_or_fetch(key, callback) returns the object as Bytes. Its asynchronous callback returns Result<Bytes, E>, charged by payload length. Empty objects are valid.

get_or_fetch_buffer accepts a callback returning Result<AlignedBuffer, E>, charges buffer capacity, and converts to shared Bytes without copying. AlignedBuffer is reexported by feuer. Both APIs have _with_disk_fallthrough variants. get checks memory and disk without invoking or waiting for a source callback. No lookup requires the object's length in advance.

Keys identify immutable content, including across restarts. Feuer stores a seed-zero XXH3-128 hash, not the original UTF-8 key. Collisions are not checked, so keys must not be adversarial.

Source: tier orchestration
Shared misses and cancellation

Concurrent memory misses with the same key and callback error type share one disk-or-callback operation. Matching callbacks must be interchangeable. Errors must implement Clone + Send + Sync + 'static, but callbacks and futures may borrow caller state.

Cancellation of the executing caller lets a waiter take over with its own callback. Completed failures are not cached. Every caller still records its own demand and completed outcome.

Optional disk-pressure decisions can use the source when at least 64 payload reads are waiting. Ordinary lookups wait for disk. See queue behavior.

Memory

Sharded object index

Each key maps to a payload. Duplicate insertions are skipped. Hits clone reference-counted Bytes, and caller-held results survive eviction.

Admission evicts the lowest-scoring object from a rotating sample, 64 candidates by default.

Source: memory store
Allocation accounting and buffer reuse

Cached allocation charges and idle buffers share a soft memory target. Entry targets are divided among shards. An oversized object empties its shard and remains cached, so retained charges can exceed the target.

get_or_fetch charges payload length. Disk promotions and get_or_fetch_buffer charge retained buffer capacity. Shared allocations are conservatively charged per entry.

cache.allocate_buffer(length) uses the same aligned pool as disk reads. Fill as_mut_slice() and return the buffer from a get_or_fetch_buffer callback. Buffers become reusable only after their last owner releases them.

All buckets share an idle ceiling of 7% of memory capacity by default. Admission frees idle buffers first. Buffer returns never evict entries. Caller-only results, active I/O, metadata, and pending writes are outside the target.

Disk

Reads and integrity

Disk APIs accept and return payloads as Bytes.

A disk index maps each object hash to its payload address, length, checksum, and metadata position. Lookups copy buffered objects or read and verify the persisted payload. They do not read neighboring objects or metadata on the lookup path.

Concurrent readers can share a read. Readers hold an address and expected checksum, not a disk reservation. Eviction may release chunks while reads are outstanding. Read errors and checksum mismatches become misses. Checksum failures remove an entry only if the index still points to the entry that was read.

A disk hit promotes the object to memory without another write. Buffered or flushing data can miss before publication.

Source: disk cache
Payload chunks and separate metadata

The first 1-MiB chunk holds a global header. Remaining chunks hold payload bytes or metadata. Each payload is a contiguous disk byte range, with 4-KiB-aligned address and storage length. Empty objects still reserve at least 4 KiB.

Entries below 512 KiB aligned size share 1-MiB chunks. Larger objects reserve consecutive chunks exclusively. Written chunks cannot be appended to. A chunk becomes reusable after its last entry is removed.

Format v15 uses 40-byte records: key hash, payload length, address, and payload checksum. A metadata chunk contains 255 record pages and one next-chunk page. Pages are 4 KiB and independently checksummed.

Disk format and write ordering
Best-effort writes and recovery

A 512-entry queue schedules disk writes after memory admission. A full or closed queue skips writes without failing lookups. Small-entry chunks flush when full, when the next small entry will not fit, or every 60 seconds. Larger entries write independently. Closing discards partial chunks. Memory eviction does not cancel queued writes.

Payload completion precedes publication. A separate periodic writer persists dirty metadata pages. Opening follows linked metadata chunks without scanning payloads and waits for all shards to recover.

Changing disk format, application payload version, or file capacity invalidates entries. There is no migration, sync, shutdown flush, or minimum recovery hit-rate guarantee.

I/O

Linux direct I/O and shared queues

Disk-enabled caches require io_uring and direct I/O. Zero disk capacity disables storage. No buffered backend is selected silently.

Pass clones of IoQueues::new()? to open to share read admission, rings, and worker threads. Shared queues allow 64 payload reads, 64 active read pieces, and 8 active writes. Waiting channels hold another 64 read pieces and 8 writes. Each physical operation transfers at most 1 MiB.

Files, capacities, indexes, histories, pools, and background-write queues remain independent. Scheduling follows arrival order without per-cache fairness. Queue counts do not cap total buffer memory.

Queue guide

Demand and retention

One counter per object

Every started lookup records its key once before checking either tier, including failures and cancellation. Raw tier reads, insertion, and eviction do not record accesses.

ObjectAccessHistories holds decayed counters independently of cache residency. The default half-life is 262,144 requests across all keys. Counters have no capacity limit and are not persisted.

The default scorer weights avoided fixed and per-byte retrieval costs by decayed demand, then divides by memory allocation charge or disk payload length. Separate tier scorers can share the same history.

Custom scorers receive the key hash, payload length, tier-specific size, and history. Scores must be finite. Scoring runs under shard locks, so avoid I/O and cache re-entry.

Limits

Feuer is a performance layer, not authoritative storage. It offers no durability guarantee, source client, source retry scheduler, hard process-memory limit, or multi-process access to one file.
