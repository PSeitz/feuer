01feuer

Request lifecycle

Checks memory, then disk, then your download callback; queues disk writes in the background. 3 components · expand to explore
TieredMemoryDiskCacheChecks memory, then disk, then your download callback

Call get_or_fetch with an object key, a byte range, and a function that downloads missing data. It returns the requested bytes. Each request is counted before looking in the cache, even if it later fails or is canceled.

The public boundary hashes the key's UTF-8 bytes once with seed-zero XXH3-128. Both tiers and request history use only that 128-bit identity; full keys are not retained or checked for collisions.

  1. Check memory for one range covering the request.
  2. On a miss, read and verify a covering disk entry. Promote only the requested bytes to memory.
  3. On another miss, invoke this call's download callback and validate its coverage.
What happens after a successful download?

The cache keeps the download in memory and queues it for writing to disk. This does not count as another request.

If disk already has the downloaded range, the cache returns the requested bytes without storing another copy. If memory already has the range, it also skips the disk write.

Download callbackYour source implementation, not a built-in S3 client

The async callback returns a Download: a starting offset and non-empty Bytes covering at least the requested range. Feuer returns an exact slice.

If several requests miss the cache at once, each calls its own download function. Feuer does not combine downloads or retry failures; your function must do that if needed.

Input and error contract
  • Keys identify immutable content and must not be adversarial; hash collisions are not checked.
  • Distinct requested ranges for a key must not overlap; exact repeats are allowed. A download can cover several requests.
  • Callback errors and downloads that do not cover the request are returned as typed errors.
  • Disk read uncertainty becomes a miss, allowing the callback to serve the request.

Stale entries, publication, and cancellation

Each queued write carries its download, key hash, and exact range. The worker checks that this key and range remain cached before starting; publication rechecks them under the memory shard lock while holding the disk index lock. No memory operation acquires a disk lock.

Eviction, replacement by a different range, or trimming can make a candidate stale. Reinserting the same immutable range allows an earlier write to proceed. Issued writes retain disk reservations through completion; abandoning the result cannot make their chunks reusable early.

Batches drain immediately available work: no batching timer or public flush API. Failed writes are logged and are not published.

02feuer-memory

Memory cache

Keeps downloaded bytes in RAM and removes or shrinks entries when it needs space. 3 components · expand to explore
MemoryCacheShardMaps object keys to cached byte ranges

MemoryCache splits keys among shards so requests for different shards can run without sharing one lock. Each shard stores an object's cached ranges in a BTreeMap, sorted by starting byte offset.

A lookup needs one entry covering the entire request; it does not assemble several cached ranges.

Index structure and admission rules

ObjectEntries owns the ordered ranges. Each MemoryEntry holds its byte range, Bytes, allocation charge, candidate slot, and admission request clock. Entries are identified by key hash and exact range, not an entry ID or generation. Request history is stored separately and shared by both tiers.

If the bytes are already cached, the new copy is skipped. A larger range replaces smaller entries it fully contains. Ranges that overlap only partly can both stay cached.

Default shard count: four times available parallelism, capped at 64, with a minimum of one.

feuer-memory/src/store/shard.rs
Memory usageCached bytes and reusable read buffers share the memory target

The cache retains reference-counted Bytes. Hits return slices sharing their allocations; there is no dedicated slab or arena allocator for cached payloads.

The memory target covers cached data and unused read buffers kept for reuse. For data read from disk, the cache counts the whole buffer, even if it keeps only a small slice. For downloads, it counts the returned byte length. Each shard gets a share of the target, but can exceed it to keep one oversized entry.

Why the target is not an RSS limit
  • Caller-held slices survive eviction and may keep a larger allocation alive.
  • Metadata and access histories add memory beyond payload accounting.
  • Pending disk writes and I/O buffers have separate ownership and accounting.
  • The memory cache owns one aligned buffer pool, charged to the same capacity.

Range trimmingKeep useful subranges rather than the whole download

When memory is full, the cache chooses an entry to remove. If only parts of it have been requested, it can copy those parts into smaller buffers and discard the rest. Otherwise, it removes the whole entry.

Trimming grace
64 requests across all keys
Minimum payload saving
25%
Copy outside the lock, validate before publishing

Overlapping or adjacent observed intervals are merged and copied into independent Bytes. Copying occurs outside the shard lock.

Publication requires the exact source key and range to remain cached. Reinsertion of that immutable range, changes to neighboring ranges, and new requests do not invalidate the copy. Retained ranges already covered by another entry are skipped. If the source disappeared or was replaced by a different range, admission falls back to eviction.

There is no periodic compaction. Caller-held slices remain valid.

03feuer-storage

Disk storage

Stores bytes on disk, tracks where they are, and checks their checksums when reading. 5 components · expand to explore
DiskCacheFinds stored byte ranges and verifies their checksums

DiskCache keeps a lookup table in RAM: object key hash and byte range → payload region, checksum, and metadata slot. Each DiskCacheShard has its own table (DiskEntryIndex), chunk allocator, cached metadata pages, and async metadata I/O lock.

A hit verifies the whole covering entry, then returns the requested slice. It does not load neighboring entries or metadata.

Concurrent reads and integrity failures

Concurrent readers of the same stored entry share a OnceCell result containing verified bytes or failure. The index holds only a weak reference, so it is not a persistent payload cache.

I/O errors or checksum failures invalidate matching disk state and return a miss. Read guards protect the physical regions during reads; returned bytes retain no disk ownership.

Whole-entry verification means small subrange requests may read much more than the requested bytes.

Disk shard count is capacity divided by 128 MiB, clamped to 1–64. Each shard owns a fixed consecutive disk byte range; its count is independent of memory and history shards.

feuer-storage/src/disk_cache.rs · DiskCache
DiskChunkAllocatorReserves and frees consecutive 1-MiB chunks

DiskChunkAllocator tracks free consecutive chunk runs in a BTreeMap. It reserves chunks in disk-address order and merges adjacent runs when chunks are released.

Each reservation is one consecutive run of whole chunks. An entry is never assembled from scattered free chunks. A failed reservation consumes no space.

Fragmentation and pressure eviction

Written payload chunks stay unchanged until all owners and read guards release them. Removing an entry leaves holes that cannot be reused individually; live neighbors can keep a mostly empty chunk unavailable. Metadata chunks remain reserved, with reusable record slots.

Pressure eviction samples entries using the shared retention score. Per shard batch, work is limited to 64 sampling attempts and a chunk budget of 4,096. Each removed entry charges its reserved region's whole chunk count, even if pending metadata invalidation, neighbors, or readers prevent those chunks from becoming free. Exhausting a budget skips further reclamation for that batch.

Shards allocate independently: space elsewhere does not guarantee admission in this shard. There is no background cleaner relocating neighbors.

feuer-storage/src/allocation.rs · DiskChunkAllocator
DiskRegion & ChunkGuardKeep space unavailable until its users finish

The allocator keeps a free list in RAM. Writers call reserve_chunks() to take space from that list before writing. A DiskRegion represents a reserved byte range in the backing file; slices share ownership of the entire consecutive run of chunks.

A read creates a ChunkGuard from the indexed entry while holding the index lock. The guard keeps the whole reservation alive through reading and verification. Eviction can remove the entry, but reuse must wait for completed metadata invalidation and all remaining owners and guards.

Example: reading an entry in chunk 7
  1. A reader finds the entry and creates a guard.
  2. Eviction removes the entry and clears its metadata record in RAM. Pending invalidation and the guard both retain the payload reservation.
  3. The I/O queue retains a guard through completion, even if the caller cancels.
  4. The next write completes metadata invalidation before releasing pending payload ownership. After all owners and read guards are gone, ChunkReservation::drop() returns the chunks to the free list.
  5. A later writer can reserve that space and overwrite it.

No code scans for guards. Reference counting controls when space becomes free. This is not a read/write lock: raw file writes do not check guards. Payload writes use newly reserved regions; mutable metadata updates use separate per-shard read/write synchronization.

Multiple reads can run concurrently. Returned bytes live in RAM and retain no disk reservation.

Batch packing & disk formatImmutable payload chunks, separate mutable metadata

Explicit batches group small entries into immutable 1-MiB payload chunks, with 4-KiB-aligned addresses and storage lengths. Each entry occupies one contiguous byte range with no metadata gaps, even across chunk boundaries.

Separate 1-MiB metadata chunks contain checksummed 4-KiB pages. Their records are updated in place under the shard's metadata I/O lock. Payload writes complete before metadata records are written; metadata writes complete before publication.

Packing constraints and persistent metadata
  • Batches sort payloads smallest first within each shard. Small entries share a chunk only when their complete aligned payloads fit inside it.
  • Multi-chunk entries own consecutive whole chunks exclusively, including unused tails. Partially filled payload chunks are finalized; later batches cannot append.
  • The v11 format stores fixed 48-byte records: 128-bit key hash, object range start and length, payload address, and seed-zero XXHash64 payload checksum. Payload length equals the object range length; storage length rounds up to 4 KiB.
  • The first 255 metadata pages hold 84 records each: 21,420 entries per metadata chunk. The final 4-KiB page stores the next metadata chunk address. Every page has its own seed-zero XXHash64 checksum.
  • Metadata chunks stay reserved while open; cleared slots are reused across batches. An active shard needs at least one metadata chunk in addition to payload chunks. A one-chunk cache has no room for payloads.
  • Cached metadata pages and free-slot bookkeeping consume RAM outside the retained-memory target. Sharing a metadata chunk does not couple payload-chunk lifetimes.

New metadata chunks are initialized before linking. Record invalidation writes complete before payload ownership is released for reuse. No fsync or fdatasync is issued; completion is not a crash-durability or power-loss ordering guarantee. Older formats are not migrated.

Restart recovery during openFollow metadata links before serving requests

Opening waits for every shard's metadata recovery before returning the cache. Each shard runs recovery on Tokio's blocking pool, using io_uring reads to rebuild its in-memory index and payload ownership.

Metadata-only reads, validation, and repair

Each chain starts at its shard's first chunk and follows last-page links, with one 1-MiB read per metadata chunk. Recovery never scans payload chunks. There is no inventory file, periodic address checkpoint, or persistent free-space map.

All metadata chunks in a shard are reserved before entry records can claim payload chunks. Record decoding checks range arithmetic, alignment, file bounds, key-hash shard identity, and conflicting payload byte ranges. Entries sharing a payload chunk share its reservation.

Zero-filled chunks, read failures, invalid addresses, cycles, or corrupt links end the chain. Corrupt record pages are discarded independently. Repairs remain in the cached metadata image and are flushed before subsequent writes can reuse space; temporary allocator claim bits are released after recovery.

Payload checksums are verified on hits, not during recovery. Missing or torn payloads become misses. Closing preserves live metadata records for the next open. Recovery remains best-effort, not durable storage.

04feuer-storage

I/O & buffer memory

Sends reads and writes to Linux and provides the memory buffers they use. 3 components · expand to explore
DataFileReads and writes the backing file using Linux direct I/O

DataFile opens the backing file with O_DIRECT and exclusively locks the cache directory. Linux, usable io_uring, and compatible alignment support are required; there is no buffered fallback.

Alignment, splitting, and caller responsibilities
  • Reads accept arbitrary ranges; physical reads round outward to 4 KiB and results are sliced.
  • Write offsets and lengths must be multiples of 4 KiB.
  • Large operations are split into requests of at most 1 MiB of physical I/O.
  • The upper layer prevents conflicting physical reads/writes and owns disk-region reuse protection.
  • Multi-request operations are not atomic. Completion is not a crash-durability guarantee.
feuer-storage/src/file.rs · DataFile
ReadQueue & WriteQueueSend reads and writes to separate io_uring workers

Reads and writes each have a bounded waiting channel, active request slots, an io_uring ring, and a worker thread. Arrival order determines scheduling, not completion order. Neither queue checks for overlapping disk ranges.

Admission and completion lifetime

Normal submissions reserve channel capacity before preparing request buffers. Startup recovery tries to reserve a read-channel slot and retries later if full. A payload read allocates its whole-entry buffer before submitting 1-MiB slices sequentially, so queue slot limits do not cap total read-buffer memory.

An eventfd wakes workers for new requests or shutdown; no busy polling or registered buffers are used. Submitted buffers survive caller cancellation. Last-handle drop drains and joins the workers.

Abnormal driver failure retains uncertain active buffers and the directory lock until process exit rather than risk unsafe reuse.

AlignedBuffer & BufferPoolAllocate and reuse aligned memory for direct I/O

Direct I/O needs memory addresses aligned to 4 KiB. AlignedBuffer allocates that memory. BufferPool keeps unused buffers in six sizes so later reads can reuse them. A read returns only the requested bytes, but caching them counts the whole buffer toward memory usage.

Allocation lifetime and configuration

Fresh aligned buffers use alloc_zeroed and matching dealloc. After the last owner releases a buffer, it returns to its cache's pool only if both the idle pool and the shared memory budget have room; otherwise it is freed.

The I/O buffer holds the disk read guard through completion, then drops it before returning Bytes. Returned results retain only RAM, not disk reservations, and do not keep the pool alive.

FEUER_IDLE_BUFFER_POOL_PERCENT sets the idle ceiling (0–100; default 7). Zero disables idle retention. Cached entries take priority: admission frees idle buffers as needed, and returns never evict entries.

Writes reuse aligned input slices or allocate unpooled scratch buffers. Active reads and caller-only results remain outside the retention budget. Standalone storage without a memory cache retains no idle buffers.

05feuer-types · both tiers

Shared retention policy

Uses request history to choose which entries to keep and which to remove. 2 components · expand to explore
ObjectAccessHistoriesTracks requested byte ranges independently of cached entries

ObjectAccessHistories remembers which byte ranges people request and how often. Memory and disk use the same history when choosing entries to remove. get_or_fetch records each request before lookup, including failures and cancellations. Adding or removing cached data does not change that history.

Two histories with different purposes

Scoring counters: decayed counts per exact requested range. Default half-life is 8,192 requests across all keys. Distinct keys and range counters are never removed or capped during the history object's lifetime, even after both tiers evict the data.

Trimming history: a separate bounded event history. Defaults retain up to 64 events per object, aged out after 262,144 requests across all keys.

History uses 64 independently locked maps and one global request clock, separate from memory and disk shard counts. It is not persisted; aging is request-based, not wall-clock-based.

feuer-types/src/retention.rs · ObjectAccessHistories
Value scoring & sampled evictionPrefer more avoided retrieval cost per retained byte

Only requests fully contained in an entry contribute to its value:

Σ decayed_count × (fixed_request_cost + requested_bytes)
──────────────────────────────────────
retained_bytes

Both tiers sample candidates and choose the lowest value per byte. Memory divides by the entry's charged allocation capacity; disk divides by payload length. Memory may trim that victim; disk removes selected entries.

Defaults and what the score excludes
  • Sample size: 64 live candidates per decision, configurable.
  • Fixed request cost: 10,000,000 equivalent bytes by default; zero scores bytes only.
  • Both tiers maintain dense candidate lists sampled in rotation; removal leaves no stale-candidate backlog.
  • Disk alignment, metadata, and chunk overhead do not enter the payload-only score.
  • Tier-aware memory valuation based on disk residency is not implemented.

Settings include FEUER_RECLAIM_SAMPLE_SIZE, FEUER_ACCESS_COUNT_HALF_LIFE, and FEUER_FIXED_RETRIEVAL_EQUIVALENT_BYTES.

06cross-cutting

Types, runtime & visibility

The types and settings you use, the metrics you can collect, and the current limitations. 3 components · expand to explore
Types & configurationKeys, byte ranges, downloads, and cache settings
  • ObjectKey: public UTF-8 string identifying immutable content.
  • ObjectKeyHash: internal seed-zero XXH3-128 identity shared by both tiers, history, and recovery; full-key collision checks are not performed.
  • ByteRange: an exact, non-empty byte interval.
  • Download: starting offset plus non-empty bytes, with a derived range.
  • CacheConfig: cache directory, fixed disk capacity, memory target, and reclaim sample size.
Opening a cache and selecting a runtime

Public opening is asynchronous, requires a Tokio runtime, and waits for all disk shards to recover. Disk capacity must be a positive multiple of 1 MiB, including alignment and metadata overhead.

feuer-tokio lets the code use either Tokio or madsim's Tokio replacement for deterministic tests. Enable one runtime feature, not both.

Current boundariesWhat this implementation does not provide yet
  • No crash-durability guarantee. Open waits for best-effort recovery; writes are not synchronized to stable storage.
  • No buffered I/O mode. The disk tier requires Linux direct I/O and io_uring.
  • No built-in source client, download coalescing, or retry scheduler. Those belong to your callback.
  • No hard total-memory cap. Active reads, caller-held buffers, queued writes, cached metadata pages, and uncapped request-history counters sit outside the retained-memory target.
  • No multi-entry range assembly. One cached entry must cover a request.

The disk layout and allocator remain experimental; this explorer describes the current implementation, not a stable on-disk interface.
