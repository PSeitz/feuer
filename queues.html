Lookup → memory → disk → callback

Read pathforeground · await

A memory miss checks the disk range index. If an entry covers the request, the lookup waits for an integrity-checked disk read.

Disk range hit→Read admission→Read ring
Channel admission64 waiting + 64 active

A Tokio mpsc::channel(64) reserves waiting-channel capacity with reserve().await. A full channel yields the submitting task rather than blocking its executor thread.

Reserved capacity for preparing requests and queued requests share the channel's 64-position limit. The worker has 64 additional active slots; receiving a request frees channel capacity, not completing it. Callers waiting to reserve are outside these counts.

There is no raw-I/O byte budget. A payload read allocates its whole aligned entry buffer before reserving channel capacity for each physical read of at most 1 MiB, so request counts do not cap read-buffer memory.

Startup recovery uses the same reserve().await admission before allocating each 1-MiB metadata-read buffer. Opening waits for all shard recovery to finish before serving lookups.

Channel → activeno pending list

Submission sends through the reserved channel permit without another admission wait, signals the worker's eventfd, then awaits a oneshot reply.

The worker receives requests in channel order directly into free active slots. When all slots are occupied, requests stay in the channel. Each active slot owns its request and buffers through completion; there is no intermediate pending list.

Verification → memory promotionslice / full buffer

For a stored entry, the disk cache reads and hashes the entire covering entry, excluding alignment padding and without reading metadata or neighboring entries. Concurrent readers of the same stored entry share its I/O and verification. Hits in unfinished small-entry buffers instead copy only the requested bytes without disk I/O.

Readers retain an address and expected checksum, not a disk-region guard. Eviction can release chunks for reuse while a read is outstanding. Corrupt or uncertain data becomes a miss and falls through to the callback; validation is subject to checksum collisions. A disk hit does not schedule another disk write.

Only the requested slice is returned and indexed in memory. Promotion copies it when the destination buffer has smaller backing capacity; allocation failure retains the original slice. Memory admission charges the chosen buffer's whole capacity. A small request can still require a large whole-entry read.

Disk-write queue256 entries · skip if full

After a callback download is admitted to memory, Feuer attempts to schedule a disk copy. This is a separate queue above the raw write-I/O queue.

Download admitted to memory→try_reserve→Disk-write worker
Full means skip, not waitTokio mpsc

The channel holds up to 256 queued entries. try_reserve() returns immediately. Full or closed queues skip disk writes without failing the successful lookup.

Queued and active payload bytes are tracked, but have no byte cap or separate memory-cache charge. The queue can keep a payload alive after its memory entry is evicted.

One worker, small-entry chunks60-second partial flush

Each shard always owns an initialized 1-MiB small-entry buffer, shared by queued writes and explicit batches. Copying releases incoming bytes. Flushing reserves payload chunks; metadata positions are taken only at publication. Full/no-fit chunks flush immediately; the worker drives a 60-second flush timer even when idle. Larger entries write separately. Closing discards partial chunks.

Lookups can copy requested bytes from buffered entries after memory eviction. Busy/flushing chunks may miss until publication. Queued and active writes proceed independently of memory retention; payloads occupy contiguous aligned disk byte ranges, separate from metadata.

Write completion ≠ publicationkey + range rechecked

Payload writes finish before publication and in-memory metadata updates. Dirty metadata pages write every second, independently; failed writes are not retried. No fsync, fdatasync, or shutdown metadata flush is issued.

Publication rechecks disk containment, not memory residency. The writer owns reservations while awaiting I/O, but cancellation can release them while submitted writes continue. Written chunks cannot be appended to; they become reusable after their last entry is removed, without waiting for readers or metadata writes. Removal makes metadata slots reusable without invalidating old on-disk records. Late writes to reused chunks can cause checksum misses.

Write-I/O queue8 waiting + 8 active

Same admission and worker machinery as reads, but with its own channel, active slots, thread, and ring. The two rings belong to the backing file and are shared by its disk-cache shards.

Payload + metadata writes→reserve().await→Permit send→Write ring
Why depth 8, not 64?local SSD measurement

The current code caps active writes at 8, with a separate 8-request waiting channel. Its comment cites local-SSD measurements: 1-MiB writes saturated at QD8; QD64 added no write-only throughput and increased write p99 from 4.6 to 47 ms, while worsening small-read latency.

This is hardware/workload-specific evidence, not a universal optimal depth or a measurement of the current metadata-write pipeline.

Two kinds of write pressureskip vs await

Disk-write queue full: the lookup skips scheduling a disk copy.

Raw write channel full: the background work awaits a channel reservation. The successful lookup does not wait for that disk write.

Preparing and queued writes share eight channel positions; up to eight more writes are active. Each physical operation transfers at most 1 MiB, but input slices can share larger backing allocations. There is no byte-budget semaphore.

Inside each I/O workerwake → submit → complete

Each direction has one thread owning its ring. Physical I/O requests are aligned to 4 KiB and at most 1 MiB; a logical cache read can require multiple I/O requests.

Sleep without stalling new workring fd + eventfd

The loop collects completions, receives incoming requests only into free active slots, and submits. Once all prepared submissions have reached the kernel, it sleeps in poll watching both the ring and an eventfd.

New submissions signal the eventfd, so fresh work can wake the worker even while a slow operation is outstanding. It does not continuously spin.

Completion and cancellationoneshot reply

A completion identifies its active slot. Full completion sends buffers or an error through the request's oneshot channel and frees that active slot. Channel capacity was already released when the worker received the request.

  • Still queued: requests whose reply receiver is closed are discarded when the worker receives them.
  • Already active: buffers stay owned through completion, even if the caller has gone away.
  • Interrupted or aligned short I/O: retry the remaining work. Invalid short completion becomes an error.
  • Normal shutdown: drain outstanding work, then join the worker.

Each worker receives two standard-library synchronous channels: one for reads, one for writes. Requests are routed by partition.id() % threads.

What happens when a channel fills?blocking send

Submission calls SyncSender::send before returning the asynchronous completion handle. If the channel is full, the calling thread can block until a worker receives an item.

The completion wait is still asynchronous. The distinction is specifically queue admission, not whether Foyer supports async I/O.

Queued capacity ≠ in-flight depthdifferent boundaries

The two channels can each hold 4,096 waiting requests. Separately, the ring limits combined in-flight reads and writes to the configured depth, 64 by default.

Like Feuer's waiting-channel limits, these capacities exclude operations already removed for submission. Feuer separately allows 64 active reads and 8 active writes; Foyer's active limit is shared between directions.

These are request counts, not payload-byte limits. This comparison covers the shown driver, not all memory limits in Foyer's upper storage layers.

Weighted schedulershared depth · default 64

One worker chooses between both input queues and submits to one ring. Reads and writes share the same in-flight limit.

How does it choose?read/write weight

When read_inflight < write_inflight × weight, try reads first; otherwise try writes first. If the preferred channel is empty, try the other.

Default weight is 1.0. This is a target in-flight ratio—not a fixed 32/32 partition, a bandwidth guarantee, or preemption of already-submitted work.

What is configurable?threads / depth / weight
  • with_threads: number of workers/rings; default 1.
  • with_io_depth: shared ring depth per worker; default 64.
  • with_weight: desired read/write in-flight ratio; default 1.0.
  • CPU affinity, SQPOLL, and IOPOLL are also available. Both polling flags default to false.

Worker loop & completionscontinuous userspace polling

The worker tries to fill the ring, submits when there is in-flight work, drains completion entries, and repeats. The shown loop has no sleep or blocking wait when idle.

Userspace polling is not SQPOLLtwo different mechanisms

This continuous loop runs in Foyer's worker thread even with SQPOLL and IOPOLL disabled. Those optional flags control separate kernel-side behavior.

Feuer instead blocks in poll until a ring completion or eventfd wakeup. That avoids idle spinning, but wakeup cost versus polling latency remains a measurement question.

Returning to the calleroneshot reply

Completion data identifies the request context. The worker decrements the appropriate in-flight counter and sends its result through a oneshot channel.

The caller's asynchronous I/O handle awaits that channel and returns the buffer with the result. Separate completion channels do not mean separate read/write rings.
